# CRM/Sales module relation register

Date: 28 September 2026

Scope: live Nocoly HAP app `CRM odoo` (`6cb4d051-a33c-4bf9-b56f-5f47f0e85dc9`)

Evidence: read-only HAP field metadata, refreshed `ca1phas/odoo` remote refs, Odoo 19 Community manifests, and the repository's Nocoly hand-offs. No HAP object or record was changed.

## Why this register exists

The repository already contains a strong dependency catalogue:

- `nocoly/data/manifests.json` records Odoo addon dependencies;
- `nocoly/data/connections.json` and `nocoly/data/refs.json` record module/model connections;
- `nocoly/plan/phases.json` records planned worksheet dependencies;
- `nocoly/README.md` defines Foundation, domain modules and named bridge packs;
- `nocoly/worksheets/*.md` records worksheet-specific implementation and review evidence.

What was missing was one compact register of the **currently implemented live CRM/Sales relations**. The planning graph cannot replace this register because the live app has moved beyond several older hand-offs and already contains CRM, Sales, Activities and Invoicing links.

## Odoo module baseline

The local Odoo 19 source defines these relevant dependencies:

| Odoo addon | Direct dependency meaning |
|---|---|
| `crm` | Uses Sales Teams, Mail/Activities, Calendar, UTM and Contacts. |
| `sale` | Uses Sales Teams, Accounting/Payment and UTM. |
| `sale_crm` | Auto-installed bridge that depends on both `sale` and `crm`; it connects opportunities with quotations/orders. |

Nocoly's physical packaging does not need to copy Odoo's addon boundaries one-for-one, but the ownership and bridge concepts should remain explicit.

## Gaps and decisions versus Odoo

1. **CRM-Sales bridge direction:** Odoo's `sale_crm` owns the opportunity link on the quotation/order side. The live HAP register exposes `Leads -> Orders`, while Orders has no direct Lead Relation in the current field read-back. The behavior may still work through workflows, but the bridge should have an explicit acceptance test: create a quotation from a Lead, open both sides, and prove stable traceability after edits.
2. **UTM Campaign completeness:** the earlier conformance review found that Campaigns lacks Odoo's Stage and Tag relations. Keep this as an acknowledged parity gap until those UTM models are intentionally added.
3. **Activity scope:** the current Activities model relates to Leads only. It is useful CRM functionality, but it is not yet Odoo's polymorphic activity engine across Contacts, Orders and Invoices.
4. **Invoicing is already coupled:** Sales, Contacts and Products currently reference Invoicing configuration and transaction objects. A client copy cannot remove the Invoicing section safely just by deleting its menu or worksheets.
5. **Recurring Plans:** the worksheet exists but the live Leads Relation inventory does not consume it. It is a candidate for omission in client copies when recurring revenue is not enabled.

## Safe customization and removal rule

For each client copy, classify every module as `keep`, `remove`, `replace`, or `future`. Before removing a module:

1. search Relation fields that target its worksheets;
2. search workflows, custom actions, business rules, views, charts and custom pages that reference it;
3. decide whether dependent fields are removed, replaced with snapshots, or redirected;
4. remove the consumer references before the provider worksheet;
5. read back the remaining structure and perform a rendered UI smoke test.

This means “master app with unwanted modules removed” is viable, but removal is a dependency operation, not a navigation operation.

## Upgrade and product strategy

A forced uniform upgrade across all customized client copies is not required. However, “no uniform upgrade” should not become “no baseline or version tracking.” Keep:

- one maintained master template;
- this relation register and a module manifest;
- a change catalogue with bug fixes versus optional features;
- a per-client list of enabled modules and local overrides;
- opt-in backports for shared bug/security fixes.

New customer functions can then be built locally. Reusable behavior should return to the master as an optional module/bridge; customer-specific behavior should remain an override.

## Multi-company deployment decision

Using **one copied HAP app per company** is valid when the companies need strong isolation, different administrators, materially different customizations, and no shared operational data. It is better described as **multi-instance deployment**, not Odoo-style Multi-Company.

It is not equivalent to Odoo Multi-Company when users need to switch companies inside one system, share Contacts/Products, consolidate reports, or automate inter-company transactions. Separate apps duplicate master data and require fixes/schema changes to be applied to every copy.

Recommended rule:

| Situation | Recommended design |
|---|---|
| Different external customers or highly independent companies | One app copy per company/customer. |
| One group with multiple legal entities but no shared operations | Separate apps are acceptable; optionally aggregate into a read-only reporting app. |
| One group needing shared masters, company switching, consolidated reporting or inter-company flows | Use one governed suite with a Company master and Company Relation on company-dependent records, or separate operational apps plus an explicit shared-core/reporting integration. Do not assume “one more app” alone provides Multi-Company behavior. |

## Maintenance ownership

This register should be updated whenever a Relation is added, removed or redirected in CRM, Sales, shared master data or their bridge modules. Worksheet hand-offs remain the detailed implementation evidence; this file is the cross-module removal and packaging index.
