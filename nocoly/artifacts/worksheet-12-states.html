Worth knowing before you review

A duplicate state code is caught a second after the save, not refused at it

Odoo's constraint is a pair — unique(country_id, code) — and HAP has no equivalent. The first build put HAP's No duplicates on a hidden composite formula; it refused nothing, in the API or the form, so the owner had it dropped. Measuring the alternatives turned up something worth knowing on its own: the same switch that refuses an API write with resultCode 11 is simply ignored when a workflow does the writing — same control, same value, minutes apart.

So the workflow does the checking itself. A state that repeats a code its country already uses is saved — nothing in HAP can refuse it — and then, within seconds, loses its key, gains a ticked Duplicate code, and appears in the Duplicate codes view, while its workflow run stops at an abort node. Mend the code and the tick clears and the key is written. The invariant is: a state holds the key its code implies, or holds none and is ticked. All 2,102 seeded states hold theirs; none is ticked.

What it changed elsewhere

  • Countries gained States, the reverse relation, read-only, as a list at the foot of the country form with the same two columns Odoo shows there. Its remark block no longer says the states are still to come.
  • Contacts: State became a relation (state_id) in the text field's place beside City, eight contacts carried — seven in Selangor, one in Sarawak — read back, and then the text control deleted. The two address automations were re-pointed at the relation first, in the four places that named it.
  • The picker is not narrowed by the contact's country, because Odoo's is not: its partner form passes default_country_id, which name_search does not narrow on. Typing Aceh on a Malaysian contact offers Aceh (ID), and picking it moves the contact to Indonesia.

Roles — Odoo's answer, and it differs from Countries

Odoo puts res.country.state behind base.group_partner_manager — a contact manager — with read, write, create and delete, where res.country needs a settings administrator; its own Fed. States list even carries a New button where the Countries list does not. So States takes each role's Contacts cell: Accounting Administrator full, Accountant and Invoicing add and edit, Accounting Read-only reads. Delete stays with Accounting Administrator, the standing rule. Seen on screen: as Invoicing, States offers + Record and Countries does not.

Built by nocoly/build/states.py; the 2,102 records went in in under five minutes and every one was read back. The data was reconciled with the tenant per country, by digest rather than copied through the browser: ten countries differed — six the Odoo checkout lacks entirely and four whose contents differ, Saudi Arabia 13 against the checkout's 93 — and after those were read out of the tenant, both sides agreed exactly: 2,102 states in 74 countries, Malaysia 16, every country's hash identical.

Two things the build learned: HAP has no "a Relation is not" operator, so E and F are built with the condition inverted — the conditioned path carries nothing and the write hangs off the else path; and two writes seconds apart race the workflow runs they start, which produced a false failure before the test, not the build, turned out to be wrong.

Tests and differences

Seventeen checks in the browser

Fifteen pass. The view, its three columns and the Country filter (Malaysia 18); Selangor field by field with its Selangor (MY) title; the create form with Odoo's help under each field; a country's States list; the relation on a contact; the picker offering Aceh (ID) to a Malaysian contact; and the address push carrying the state down to a company's people and not to its invoice and delivery addresses.

Workflow E was proved in the form — setting a contact's state to Aceh moved its country to Indonesia — and workflow F through the API: writing only the country cleared the foreign state. The rebuilt duplicate check was then run end to end: a third Malaysian ZZ-01 typed into the form saved, then lost its key and gained the tick; mending its code cleared the tick and wrote the key; the Duplicate codes view listed exactly the offenders and nothing else; and not one of the 2,102 seeded states is ticked. One test could not be isolated: changing only the country in the form, where what the form sends decides which workflows match — the single run ended with E's write winning. It is worth a reviewer's minute.

Differences from Odoo

  1. 1
    A duplicate code is caught after the save, not refused at itHAP behaviour

    Odoo's database refuses the second state. Here it saves, then loses its key, gains a tick and lands in the Duplicate codes view until someone mends it. See the note at the top.

  2. 2
    A save that changes both fields does both thingsHAP behaviour

    Odoo's onchanges fire one at a time, so you never get both. Here the country is written from the state and the state is cleared, and the contact ends in the state's country with no state.

  3. 3
    The tie at equal codeSorting

    Odoo orders code, id — creation order within a code; ours breaks the tie on Country Name.

  4. 4
    A country's States list is newest firstHAP behaviour

    Odoo's list at the foot of a country is in code order.

  5. 5
    No editable list, no New button on a countryScope

    Odoo lets you type a state straight into the list at the foot of the country form; here a state is a record of its own.
