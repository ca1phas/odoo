Nocoly Expansion Map

Odoo looks like a tangle of interconnected apps. It isn't — half its codebase exists purely to hold apps apart. That same seam is where the Nocoly build grows, one app at a time, without touching what already works.

The short answer

Odoo already solved this problem

The premise behind the question — that Odoo's apps are too entangled to copy one at a time — turns out to be false, and provably so. Odoo's app modules do not reference each other at all. Every cross-app feature lives in a separate bridge module that installs itself only when both sides are present, and that adds fields to existing models without ever editing them.

Build one app at a time by copying Odoo's own seam. Each new Odoo app becomes a new Nocoly app holding only its own worksheets. Everything it shares with Sales — Products, Customers, Taxes, Units — it reaches by Relation control pointing at the worksheet that already exists. What couples it to Sales becomes an append-only set of controls on Orders.

Nothing existing is restructured, because Odoo never restructures either.

Finding one

Half the repo is glue, not apps

Of 662 modules in the repository, 231 are country localisations and 41 are test harnesses — leaving 390 real business modules. Of those, 190 are bridges: modules flagged auto_install that depend on two or more other modules and exist solely to join them.

Odoo isn't 390 interconnected features; it's roughly 200 self-contained features and 190 connectors, kept in separate boxes on purpose. Install Sales and Inventory together and Odoo silently installs sale_stock — a third module neither of them knows about.

The apps themselves are small. Measured by transitive dependency closure, mail pulls in 6 modules, account 16, stock 16, purchase 17, crm 17. The largest application in the entire repo, website_sale, pulls 32.

Finding two

The four layers

Every module sits in one of four bands. Dependencies only ever point downward, and the top band is the only one that knows about more than one app.

L3

Bridges — the only cross-app code

Installed automatically when both sides are present. Adds fields to models it does not own. Defines no models of its own.

sale_stock · sale_crm · sale_purchase · sale_mrp · sale_project · stock_account · 184 more

L2

Apps — self-contained, sibling-blind

Each defines only its own transaction models. Contains zero references to any other app.

sale (2 models) · purchase (3) · crm (6) · project (11) · mrp (14) · stock (23) · point_of_sale (15) · hr (10)

L1

Shared master data — the real backbone

Owned by no app, needed by all of them. This is the layer that makes apps look entangled when they aren't: they don't depend on each other, they depend on this.

product → product.template, product.product, product.pricelist · uom → uom.uom · account → account.tax, account.move, account.payment.term

L0

Framework

Partners, companies, currencies, users, messaging and activities. Extended by 117 modules but owned by none.

base → res.partner, res.company, res.currency, res.users · web · mail → mail.activity.*

Note where account sits. It is the most-depended-upon module in the repo — 158 modules require it — but that is because it owns taxes and journal entries, which are master data, not because Accounting-the-app reaches into everything.

The enabling fact

Whether any of this works hinges on one platform question: can a worksheet in a new app relate to a worksheet living in the Sales app? Reading the live Orders worksheet through the v3 API answers it.

GET /api/v3/app/worksheets/6a9e38ccf363582dd3794504   → Orders, 86 fields, 18 relations

{ "name": "Customer",
  "type": "Relation",
  "dataSource": "6a9e38961204328eb1adf458",   ← bare worksheetId
  "subType": 1 }                                no appId. no app scope.

Verify once before Phase 1. The stored shape permits cross-app relations; what this cannot confirm from the API alone is whether the form designer's relation picker will offer worksheets from another app, or whether roles need widening for a user to traverse the link. Test it on a throwaway worksheet in a throwaway app — one Relation control pointed at Products, set via ws.add_controls, read back, then opened in the UI. If the picker refuses but the API accepts, build relations through the API. If cross-app relations fail outright, the fallback in rule 02 applies.

The discipline

Five operating rules

Each one is Odoo's own discipline, restated in Nocoly's terms.

01

Master data stays in the worksheets it already lives in

Do not migrate Products, Customers or Taxes into a new "Core" app. Moving them breaks every Relation, Lookup, Rollup, Formula and workflow in the Sales build — the restructuring this plan exists to avoid. Promote them in name only: record in state/ that these 29 worksheets are platform-owned and Sales is merely their first tenant.

02

One Odoo app, one Nocoly app

Purchase gets its own app holding only the worksheets Odoo's purchase module defines. Everything shared is reached by a Relation control whose dataSource is the existing worksheetId. One Products table, many consumers.

If cross-app relations turn out to be blocked, fall back to adding a new section inside the existing app and renaming the app to something neutral. That is a section-level change, not a worksheet-level one — still no rerouting.

03

Coupling ships as an append-only bridge pack

The Nocoly equivalent of sale_stock is a named, documented set of controls appended to existing worksheets plus the workflows that maintain them. Applied with ws.add_controls, never a controls round-trip, and never through direct.save on Orders. This is already the house rule for Orders; rule 03 makes it the rule for every worksheet a bridge touches.

04

Build the bridge only when both towers stand

Nocoly has no auto_install, so the trigger has to be a checklist rather than the platform. Keep one file per pair — state/bridge_sale_purchase.json — listing the controls it appends, the workflows it owns and the invariants it must not break. A bridge pack is a deliverable in its own right, scheduled after both apps are standing, never smuggled into either app's build.

05

Every phase ends on the same invariants

The existing check stands unchanged after each phase: orders S00009–S00016 = 8 orders, 21 lines, RM 961,400.65, statuses unchanged; INV/2026/0003 and 0008 untouched. A new app that moves those numbers has reached into Sales and must be backed out. This is the tripwire that proves "no major changes" held.

The order

Build the foundation once, then add towers

The foundation is already poured. Twenty-nine of the thirty-six worksheets in the Sales app are shared backbone — Products, Customers, Taxes, Units, Invoices — and every app above reuses them by Relation control rather than copying them. Each new app is a tower of its own worksheets standing on that slab, clipped to Sales by a handful of appended controls.

Before Phase 1

What to settle first

  • Prove the cross-app Relation. Throwaway app, throwaway worksheet, one Relation control pointed at Products, read back and opened in the UI. Everything downstream assumes this works.
  • Check role traversal. A CRM user who can open a Lead must be able to read the Customers row it relates to, which lives in another app. Confirm how roles behave across that boundary before designing permissions twice.
  • Write the backbone registry. One file in state/ listing the 29 shared worksheets, their IDs, and the rule that changes to them are now cross-app changes needing the invariant check.
  • Decide the Move Type append on Invoices. Cheaper now than after Phase 2, and it decides whether vendor bills are one worksheet or two forever.
  • Close out or park the paused work. Attributes & Variants is half-built with a disabled generation workflow and leftover test records; the UI click-through has an open checklist and its own records to soft-delete. Both touch worksheets the new apps lean on, so finishing them keeps Phase 1 from inheriting ambiguity.

Caveats

What the counts do and don't mean

Enterprise apps are listed but not measured. 23 of the 49 catalogue apps ship only in Odoo Enterprise and have no module in this repository, so their dependencies and bridges cannot be read from source. They appear in the catalogue above with their known module names and nothing else.

Two catalogue apps are thin wrappers. The Sales app is sale_management, which is sale plus a dashboard — the substance is in sale, so that is what is measured. Events is event plus website_event for the public site.

Repair is included though it isn't on the catalogue page, because it bridges to Sales, Purchase, Manufacturing and Point of Sale and leaving it out would make those counts look wrong.

Bridge counts are pair-level, not effort-level. One bridge can be a single field (sale_crm) or twenty-seven (sale_stock). The ring and the bar chart show how many bridges join a pair, not how much work each carries — the phase cards do that.
